# 检索任务规划

## 定义事实而非指定反复访问的网站

先明确实体、城市/地区、日期、版本与需要回答的字段。相对时间结合当前时区确定，分店或位置不明且会改变结果时询问关键缺失，不擅自选城市。只读检索不扩展到购票、下单、登录账号或修改数据。

## 选场景与来源职责

生活信息区分地址、营业时间、实时场次/票价、路线及主观体验；同一网站不必负责所有字段。技术问题优先对应版本的官方文档与上游仓库；价格统一型号、地区和计费口径；政策/统计找发布机构与适用时间；论文分清版本与实验条件。用 `research` 加最贴近场景的 topic，交给 Web 选择专项方法，不把所有领域网站清单塞进 Step。

一个连续查询通常单个 WEB Step；只有确实独立且可合并的 2–3 个方向才并行。不把同一文本读取工具的并发限制当作来源失效。需要附件阅读或产物时明确实际可用工具与交接，不默认网页摘要能支持完整文档结论。

在 `execution_guidance` 中提示 Worker 把同一事实的主查询和最多两个互补角度放进一次 `web_search`，由工具并发执行，而不是规划三次串行同义搜索。按场景写出具体示例，例如本地餐厅可用“实体候选／本地特色／近期评分”，政策可用“事项＋机关／文号／权威转载”，技术资料可用“官方文档／上游 issue／release”。第一批结果已覆盖全部 MUST 时必须提交；只有一个明确字段仍缺时，才允许针对该字段继续检索。

普通搜索、公开静态信息、登录墙和“网页可能还有内容”都不能让计划隐含浏览器兜底。`BROWSER_AUTOMATION` 只在用户原始请求明确要求登录、点击、填写、筛选、提交或其他页面动作时由首次路由单独选择；Scheduler 不在普通 Web Step 中写“必要时用浏览器”。

## 规定验收与退路

success_criteria 明确哪些事实必须有原文证据、哪些动态值需要时点、用户是否接受区间/替代方案。访问受阻时先判断缺的是哪个字段，再换相应官方或公开来源。替代来源已覆盖所有 MUST 就结束；仍缺场次等动态事实时保留缺口，不用地址页面顶替。

把“最低可交付边界”写短、写实，不把软偏好硬化为昂贵验收。用户只问“有什么推荐/比较好的”时，可要求返回若干真实候选、位置或主要特征并透明说明依据；不要自动追加“证明最热门、逐家评分、全网口碑交叉验证”。只有用户明确说“最高分、最火、对比口碑”时，才把比较证据列为 MUST。Worker一旦覆盖全部 MUST 就应提交，不能因为答案还能更丰富而继续搜索。

收到 Reporter 的失败报告，检查新尝试是否有新来源、查询条件、访问能力或其他可检验变化。相同地图、相同方式、相同失败不重复派发；选择补一个证据缺口、提出明确用户问题，或按现有协议停止。不能把 Reporter 的推测“可能反爬”当作已证明原因。

在当前文本工具下，地址/开放/附近车站先安排查运营方参观页，不把地图作为默认必经阶段；真实场次/余票/实时路线是另一层动态事实，缺能力时明确无法验收。检索过窄返回 No results 时，可以撤一个限制后重查；不要把放宽查询和绕过站点访问限制混为一谈。已有可信静态信息保留，不能以它们掩盖动态字段仍缺失。

派发前区分“参考行情”和“某店现价”：实测淘宝路径失败后ZOL可读参考价，前一种请求可验收，后一种仍只补目标店字段。Reporter仅写“换其他网站”时不足以继续，要求明确保留的事实、未满足标准、替代入口/查询及成功信号；不能重新派同一淘宝/地图路径。
