# 以产出和依赖拆分任务

## 决策顺序

1. 从用户原话提取要交付什么、哪些限制必须遵守、什么证据能证明完成。保留用户明确范围，不把自己想到的改进当成需求。
2. 判断能否由一个 Worker 直接完成。仅当能力不同、存在必须先取得的输入或需要独立交接时拆成多个 Step；不要机械生成“分析、实现、总结”三个阶段。
3. 对每个 Step 写出可观察的 objective、成功标准、输入依赖和输出。标准描述行为或内容，例如“表格保留全部匹配记录及来源”，而不是“认真处理”。
4. 按执行能力分配：阅读整理与已有简单工具交给 GENERAL；来源调查和网页交互交给 WEB；需要编写或执行代码交给 CODE。CODE 的任务契约应写清接口、MUST、SHOULD 和拟交付内容，让 Reviewer 可以独立推导测试。
5. 显式安排前后依赖。内部交接文件应有实际用途，用户交付文件应对应要求；不生成没有消费者的中间报告。独立互补的 Web 调查可用现有并行机制，需要同一状态或依赖前序结果的工作保持顺序。

## 方法与成本选择

skill_topics 只表达执行策略的主题，例如 documents、research、implementation、verification、appworld，最多三个；不要填工具名或假定它能授权工具。只填当前 Step 真正需要的主题，Worker 仍负责选具体方法。

预算应留给执行、验证和收尾。已有可信结果直接复用，只为成功标准缺口安排下一步。如果前提尚不成立且会改变整个方案，先安排能消除该不确定性的有限调查。

## 检查计划是否可执行

逐步确认：所需工具真实可用；下一步拿得到上一步产物；成功标准能由后续报告或验证观察；整条链最终覆盖用户产出。缺少真实能力时写出缺口，不能通过多安排一个 Worker 来假装解决。

## 小例子

“查参数并生成对比网页”先Web取证，再Code消费数据；交接必须是后者实际能读到的文件/结构，而非Web一句“数据已找到”。Docker实测/handoff可读、Worker的/tmp不共享，说明临时路径不能做依赖边。纯文档比较可General一步完成，不为每个动词另建Worker。


## 角色与拆步对照

- 用户要“找出符合条件的日程并调整提醒”：GENERAL一条Step内完成查找、更新和回读；同一状态直接续用，不能把每次工具调用拆成工单。
- 用户要“把多份格式不同的CSV统一清洗，输出可复跑脚本并验证边界”：CODE负责实现、测试与产物，其内部已有独立Reviewer；不把Worker与Reviewer再拆成两个Scheduler Step。
- 用户要“调研公开资料，编写分析程序，交付程序生成的报告”：在工具允许时，WEB输出带来源的资料→CODE交付可验证程序及报告→GENERAL完成指定渠道交付。每一步有不同消费者和产出，不只是换一个API。
- 用户只要查一个结果或修改一条记录，不因工具执行的是Python就强行用CODE；选择看任务复杂度和是否需要代码产物/独立测试。

检查反例：不要把同一应用的“查询目标”和“修改目标”机械拆开，因为目标编号与登录状态马上用于后续操作，拆开会增加交接和重复验证。若确实需要用户审批或新的独立输入，才保留边界；用户未要求的动作不补入计划。
