# 文件交付规划

## 先冻结授权与完成定义

只有用户明确要求取得、接收、发送、上传、回传或交付文件时，才安排对外文件交付。读取、总结、转换或生成文件本身不自动包含发送授权。交付对象只能是原始请求覆盖的精确文件或成品，接收方是当前发起请求的用户和当前会话；不得扩展到其他联系人、邮箱、网页、网盘或目录中的其他文件。

“已找到路径”“已复制到隔离工作区”“已生成文件”“已通过代码审核”都不是交付完成。只有宿主返回实际发送成功状态和可验证的消息回执，才能把交付标准判为完成。审批存疑而等待用户、用户拒绝、平台大小超限或结果未知时，必须如实保留未完成项，不得改写成文件不存在或已经发送。

## 按文件来源选择最短可验收路径

- 既有本机文件：优先安排一个 GENERAL Step 完成有界定位、必要的候选消歧、只读导入和向当前用户发送。用户给出的名称只对应一个可信候选时不要额外拆步；多个同名候选会改变结果时，由当前 Worker 直接询问用户后在同一 Step 继续。
- WEB 下载文件：若任务本身需要联网取得公开文件，安排一个 WEB Step 完成检索、下载登记和发送。已有精确下载链接或已登记候选时不要为了“更完整”重新搜索；若只取得网页事实而没有真实文件，不能声称已交付附件。
- GENERAL 生成的简单文件：在同一个 GENERAL Step 内生成、检查并发送，避免再创建一个只重复路径字符串的交付 Step。
- CODE 生成、转换、渲染、压缩或修改的成品：先由 CODE Step 生成并完成独立审核，发布为共享的已审核成品；再安排一个最小 GENERAL 交付 Step 发送该已审核成品。当前只有 GENERAL、WEB、CODE 三类 Worker，不要编造 Render Worker；渲染属于 CODE 的文件生成职责。未经审核的代码候选不得直接外发。
- 跨 Worker 交接：交接的是 Harness 已登记的 artifact 身份或已审核共享成品，不是模型抄写的一段宿主路径。只有确有角色边界时才拆步；同一 Worker 已能生成或下载并发送时保持一步完成。

文件外发会由独立审批器结合用户原始请求、当前 Step、Worker 理由及可信路径映射判断。Scheduler 只写业务目标和验收边界，不写审批器名称、内部函数、接口名或猜测的调用参数，也不要再让同一个 Step 同时写“交付给用户”和“不做对外发送”。

## Step 写法

Step objective 明确四件事：文件来源、精确对象、允许的必要加工、交付给当前用户。success_criteria 至少分别覆盖：目标文件身份已消歧；必要加工或审核已经完成；实际发送成功并有消息回执。若用户只说“Downloads 里的简历”，不要把整个目录作为交付对象；先列一层并按文件名有界查找，命中唯一候选后发送该文件。

尽量一步完成，但不能跨越真实审核边界。不要为了形式把“查找、复制、发送”机械拆成三个 Step，也不要把 Code 未审核候选和最终交付塞进同一 Step。已有成品时直接从成品进入交付，不重新生成；已有下载候选时直接复用，不重新联网。

## 正例

用户：“我 Downloads 里有一个简历，发给我。”

规划为一个 GENERAL Step：在已开放的本机目录中有界定位名为“简历”的文件；若唯一则只读导入并发送给当前用户，若有多个合理候选则在本 Step 内询问用户后继续。验收要求精确文件身份和真实发送回执。不得写“导入但不发送”。

用户：“从官网把年度报告 PDF 下载下来发给我。”

规划为一个 WEB Step：定位官网的精确 PDF、登记下载文件并发送给当前用户；官网候选已经满足文件身份后停止搜索。验收要求来源、文件摘要和真实发送回执。

用户：“把这份 Markdown 转成 PDF 发给我。”

规划为两个有依赖的 Step：CODE 负责转换、验证 PDF 并通过独立审核发布成品；随后 GENERAL 只负责发送这个已审核 PDF。第二步不得重新转换或猜宿主路径。

## 反例

- “找到文件并作为用户交付物交付，但不要实际发送。”——目标自相矛盾，应删除后半句。
- “先搜索整块磁盘的全部子目录，再逐个上传候选。”——范围过大；先列目标目录一层并按文件名有界搜索，只发送消歧后的精确对象。
- “Code 写完 PDF 后立即发送，稍后再审核。”——越过审核边界；先审核发布，再交付。
- “Web 已下载文件，再交给另一个 Worker 重新搜索同一文件。”——无新增价值；复用已登记 artifact。
