# 电影查询规划

先从原始用户要求提取影片身份、城市/区县、日期/时段及问题类型；不能把默认城市、同名翻拍或“最近”的未经核实解释写进计划。相对日期依据本轮当前时区解析；“今晚”要求实际开场时间晚于查询时刻，不能只验证“今天”。

## 先判断用户要的是哪一级结果

不要因为排片工具能够返回逐场详情，就把每个电影问题都扩大成“逐影院、逐影片、逐场次穷举”。计划范围必须跟随用户原话：

- “某城市某天有什么电影”：目标实体是**影片清单**。规划一条只读 WEB Step，优先调用 `list_city_movies(city, date)`；默认只交付去重后的影片名称，可附类型和覆盖说明，不要求逐影院展开所有开场时间。
- “某部电影某天在哪里看／几点看／多少钱”：目标实体是**该影片的场次**。规划一条只读 WEB Step，优先调用 `get_movie_showtimes(city, movie, date, after)`；只有用户问到的影院、时间、版本或票价进入验收。
- “某家影院某天放什么”：目标实体是**该影院的排片**。规划一条只读 WEB Step，优先调用 `get_cinema_showtimes(city, cinema, date)`；影院名称不唯一时才先用 `list_cinemas(city)` 消歧。
- 只有用户明确要求“全市所有影院的全部场次”时，才允许逐影院穷举。不能把“有什么电影”自行解释成这一范围。

### 正例：只问某天有哪些电影

用户原话：`帮我查下莱西电影院明天有什么电影`

这里“莱西电影院”可先按“莱西地区的电影院”理解，但不能声称存在一家正式名称就叫“莱西电影院”。生成类似下面的**一条** Step；不要拆成六家影院逐场查询，也不要增加影评 Step：

```yaml
- step_id: 1
  worker_kind: WEB
  skill_topics: [research, cinema]
  tool_access: ENABLED
  objective: >-
    查询莱西地区 2026-09-19 有公开排片的去重影片清单；
    返回影片名称，并说明猫眼当前列出影院的覆盖状态。
  success_criteria:
    - 使用 list_city_movies(city="莱西", date="2026-09-19") 或等价的真实排片数据
    - 输出去重后的影片名称；用户未要求时不展开各影院的每一场开始时间
    - 明确查询日期、城市、来源覆盖状态及未核验范围，不把“莱西电影院”伪造成正式影院名
  execution_guidance: >-
    先走一次城市日期影片清单的最短路径。只有该工具返回名称歧义、部分覆盖或错误时，
    才补充影院查询；不得因工具支持详细场次而扩大用户请求。
```

反例：先 `list_cinemas("莱西")`，再对六家影院逐一调用 `get_cinema_showtimes`，最后把全天每一场都列给用户。这个做法回答了更大的问题，制造长上下文和重复影片，也让审核误以为必须证明全市每一场。

### 正例：同时问场次和口碑时才拆两步

用户原话：`今晚莱西《某片》哪里能看，口碑怎么样？`

```yaml
- step_id: 1
  worker_kind: WEB
  skill_topics: [research, cinema]
  objective: 核实莱西今天当前时刻之后《某片》的影院与开场时间
  success_criteria:
    - 真实排片证据同时包含影片、影院、日期和开始时间
    - 排除查询时刻之前的场次；没有场次时说明覆盖范围
- step_id: 2
  worker_kind: WEB
  skill_topics: [research, movie-reviews]
  objective: 核实同一部《某片》的评分口径及有来源的主要赞评和差评
  success_criteria:
    - 核对影片身份与评分平台
    - 分开呈现可核验的正反评价，不用排片事实代替口碑证据
```

只问影院/场次/票价：安排一条只读 WEB Step，`skill_topics` 包含 `cinema`；验收只写用户实际要求的目标影片、影院、城市、日期与字段。用户明确问某部影片的场次时，以带影院名称和开始时间的真实排片证据回答；若没有核实到场次，就明确证据覆盖范围与尚未查明的部分，不编造一个场次。若用户要求全市完整列表，则要覆盖列表/分页或明确非穷尽。票价、余座只有用户要求且来源能核实时才算完成，不能从影院起价推断指定场次。

只问评分/评价/是否值得看：安排一条普通网页研究 WEB Step，`skill_topics` 包含 `movie-reviews`；验收重点是同一电影的条目身份、评分口径、实际可核验的赞/贬评价及来源，不要求影院场次，也不把影评当排片。

只有 MOVIE 工具故障、覆盖不足或影评 Step 需要公开评价来源时才安排 Web Search；在 `execution_guidance` 中要求一次调用并发主查询和最多两个互补角度，不规划连续同义搜索。排片补证可分为“城市＋影片＋日期”“目标影院＋日期”“另一公开票务来源”；影评可分为“评分条目”“观众评价”“专业影评”。任一批次已覆盖当前 Step 的全部 MUST 就提交，不为更丰富继续搜，也不把浏览器写成搜索失败后的退路。

同时问“哪里看”和“评价怎样”：拆成两条**各自可验收**的 WEB Step，一条查场次，一条查影评；两个 Web Skill 在同一 Step 互斥，不能要求一个 Worker 同时加载两个独占 Skill。当前计划执行器会逐条运行 Step，不把这两条写成同一 Step 的并行 Worker；最终答复分别给出动态场次事实与主观评价，不互相填证据缺口。只问场次时绝不为凑步骤新增影评调用。

例如用户问“今晚莱西《某片》哪里有场次，口碑怎么样”：Step 1 `worker_kind=WEB, skill_topics=["research", "cinema"]`，核实莱西、当日且晚于当前时间的影院与开场时间；Step 2 `worker_kind=WEB, skill_topics=["research", "movie-reviews"]`，核实同一部影片的评分/评论来源。两条 Step 分别写 `objective` 和 `success_criteria`，不要在“查影评” Step 中重新要求场次，也不要让影片详情页证明莱西今晚有场次，或让“有排片”证明好评。

若目标日期确实没有排片，而用户意图是寻找可看的选择，可以追加“明天”作为**明确标注的备选**，仍须先如实回答今天没有；用户明确只要今天时，不擅自把验收日期改成明天。无场次需要有效覆盖地区与日期的证据，不能由搜索工具报错、单个影院空页或猫眼不可达推断。购票/选座/付款、登录账号都不属于只读电影研究，不能暗中加入。
