# 按证据恢复任务

当前 Scheduler 在 run 开始选定方法；如果本策略已选中，后续发生失败时按下列分支处理。它不意味着运行中能够重新加载 Skill。

## 先确定失败在哪一层

核对当前用户目标、最新 StepReport / Code Review、已经完成的产物和停止原因。区分：缺少输入、缺工具或环境、实现行为错误、报告/交付缺口、方向偏离、预算用尽。模型自报失败与实际任务失败可能不同；成功 span 也不能证明用户目标已完成。

对仍有效的证据记录来源和适用版本。已验证的中间产物可复用；版本改变或前提被推翻的结果需要重新检查，不因存在旧文件就认为可继续使用。

## 选择动作

- CONTINUE：任务方向、候选和大部分成果仍有效，剩余是局部修复或补证。指令明确“已完成什么、尚缺什么、下一次怎样验证”，不要原样重发整个失败任务。
- RESTART：输入或实现方向已经失效，当前候选的局部修改不足以满足契约。说明失效原因，保留可复用的需求与事实，重新安排必要步骤。
- STOP：用户已取消、必须的外部条件无法满足，或剩余预算不足以形成有价值的执行和验证闭环。提供已完成成果、具体阻塞和恢复需要的条件。

瞬时失败只有在重试能得到新结果、且重复操作不会扩大副作用时才值得继续。若上次写操作结果不明，先安排回读确认；不要仅因超时就重复发送或创建。

## 避免无效循环

下一次执行至少要改变输入、假设、方法或可用条件之一。相同前提下连续收到同样失败，就应定位缺失条件或改变方案。服从宿主已有预算与返修上限，不自行承诺无限重试或后台监控。

## 小例子

CSV实测：报告若只说“pytest失败”无法派工；零收集且ModuleNotFoundError应先补导入入口，收集12项后两条等值断言失败才交Worker修比较符，新版本同组12通过再验收。读取报告时要拿到“阶段、版本、真实差异、可复跑入口”，缺哪项就补哪项，不把所有失败都变成重写代码。
