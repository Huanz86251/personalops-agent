# 从证据得出验收结论

## 建立对应关系

先读取任务契约和当前可见审核材料。为每项标准定位能直接支持它的工具结果、检查记录或产物内容，记录来源引用及适用版本。Step Reporter 只使用所提供的审核包与允许访问的材料，不假设能看见 Worker 未交接的历史。

区分四类证据：执行记录证明动作尝试过；回读结果证明当时的状态；检查结果证明特定输入下的行为；模型陈述只是待核对结论。文件存在、进程退出零或工具返回 OK，都需要结合当前标准判断支持范围。

## 处理缺口与矛盾

- 有直接证据：说明它满足了哪项标准，避免扩展为未测试场景也成立。
- 缺证据：记录还需要什么可观察结果，不将“未看到失败”当成功。
- 证据冲突：核对时间、版本、输入和统计口径；优先采用与当前候选及要求匹配的原始记录。暂时无法消解时保留冲突，不把两者平均成折中结论。
- 只有部分满足：保留已验证成果，指出精确剩余范围，让 Scheduler 能安排补证或修复。

同一工具输出在多个摘要中被重复引用，仍然只是一份来源。涉及总量时明确分母、缺失项与计算口径；未知用量不能算作零，局部通过不能推广为整体成功。

## 形成报告

依据角色已有 Schema 填写每项标准及证据引用，不新增输出协议。按“证据引用与观测 → 单项状态 → 整体理由 → 整体结论”的顺序填写，不能先选择完成或通过再寻找解释。只批准已检查且位于当前允许引用集合中的产物；内容无法查看时说明验证范围。结论同时给出有效成果和未解决项，重规划理由应指向具体缺口。

## 小例子

同一M650材料可产生不同判断：参考行情请求可使用ZOL具名参考价；指定淘宝店现价请求仍缺卖家/SKU实时证据。先把证据对应回原标准再判完成，不因为换网站取得数字就降低验收口径。Code的12项通过也只支持该版本和输入集合，不是所有场景。
