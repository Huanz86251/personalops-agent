# Schema 契约独立验收

## 独立建立输入矩阵

从 code_task 的公开接口与 MUST 确定字段必填、null、默认值、类型转换、范围、枚举、额外字段及跨字段语义。不需要 Worker 隐藏上下文，也不把实现中的默认行为当作用户要求。契约没规定的严格度不能凭喜好新增为阻断条件。

## 生成最小有区分度的正反例

先检查最小合法及完整合法对象，再针对每类实际约束选一个非法对象。缺失、null、空串、零和 false 分开测试；上下界测试边界本身与紧邻无效值。拒绝用例核对明确的字段/错误类别，避免“任何异常都算正确”。合法对象被误拒同样是缺陷，不能只测拒绝路径。

## 验证真实边界

先确认验证库实际在 Reviewer 容器中：本机 Code 镜像实测没有 Pydantic，宿主能导入不代表容器可用。产品若用标准库验证，就从其真实入口测试语义，不为了测试强加 Pydantic；契约明确要求某库而缺依赖则记环境缺口，不改契约或联网补包。数值输入需区分 bool 与普通数字（不能只依赖宽泛 isinstance 检查），零与缺失也分别验证。

检查入口是否真正调用了验证器；Schema 文本正确不代表调用链执行约束。经由实际生产者 → 序列化 → 消费者运行往返，检查别名、默认值、日期等值与语义。只在契约要求向后兼容时引入旧样本；不能临时要求兼容所有历史形式。类型库版本和配置不同会影响强制转换，先核对环境再判错。

## 归因并返修

失败先核对测试假设：例如 JSON Schema 的 properties 本身不意味着字段必填；契约却明确要求必填而真实入口接受缺失，才是可复现缺陷。确认问题后给 requirement ID、最小对象、期望接受/拒绝与真实结果、受影响消费者及重测方式。

不改产品代码，不靠放宽断言换通过。CSV实测在没有Pydantic的容器里从CLI测试JSON配置：零被接受，缺失/null/bool/字符串/额外字段返回约定错误；无需为Schema测试安装框架。新候选重跑失败反例与合法往返，防止加严验证误伤正常数据。报告解析成功仅证明格式，不证明业务字段正确。
