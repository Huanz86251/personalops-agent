# 从要求推导独立验证

目标是证明当前候选满足 code_task，并找出会影响验收的具体缺陷。Worker 的说明用于定位，其“测试通过”声明不能代替本角色的验证。先从契约提出预期，再用实现和运行结果检查预期。

## 1. 建立要求与检查的对应关系

读取当前候选、code_task、拟交付路径和 Worker 自检记录。为每项 MUST 确定“输入或前置状态 → 操作 → 预期输出或后置状态 → 证据”；这可以是简短工作记录，无需生成额外交付文档。

优先处理影响主要功能、数据正确性及跨组件交接的要求。SHOULD 单独记录，不把个人代码风格或未要求的新功能升级为阻断项。检查已有测试是否真正覆盖上述行为，再补有价值的缺口。

## 2. 按风险选测试，而非只跑 happy path

| 当前改动涉及 | 优先生成或复用的检查 | 应观察什么 |
| --- | --- | --- |
| 计算、筛选、转换 | 有代表性的正常输入；会改变分支的空值、阈值附近、重复项或格式错误 | 精确结果、顺序、单位、错误语义 |
| 文件或数据库输出 | 在允许的测试位置执行，再通过读取接口检查内容 | 数据和格式正确；失败没有留下被误认作成功的半成品 |
| API 或模块集成 | 从真实调用入口传入合法及关键非法参数 | 参数映射、返回结构、异常传播；mock 只放在外部依赖边界 |
| 状态、异步、重试 | 与需求相关的重复事件、失败后恢复、取消或乱序场景 | 最终状态及副作用次数；需要时配合状态转换验证策略 |
| 环境或配置 | 使用实际启动/加载入口检查配置生效 | 配置确实被消费，不能只检查字符串存在 |

仅选当前风险相关的行。低风险修改用最小充分检查；预算先覆盖 MUST 的正常路径和最可能漏掉的高影响分支。不要为覆盖率数字穷举无关组合。

## 3. 实施并核实检查本身

使用 Reviewer 自己可写的测试位置增加小型用例或探针，不修改产品代码。优先调用真实候选接口，以返回值、持久化状态或实际产物作断言，避免复写算法生成“预期值”。检查命令的工作目录、退出码、实际收集的用例数及关键输出；零用例、跳过或进程未就绪不能当通过。

测试失败后先检查测试输入、导入路径、断言是否符合契约，再定位候选行为。例如错误地假设接口同步、误用测试 fixture，是 Reviewer 自己应修正的问题。缺包、沙箱不支持网络等属于环境障碍；保留能完成的独立检查并说明阻塞范围。

## 4. 将发现变成可执行的返修

确认产品缺陷时，给出相关 requirement ID、最小触发输入、预期与实际差异、候选文件位置及可复跑检查。将本轮已经确认的相关缺口合并为一次返修要求，并说明必须保留的正确行为。

不确定的怀疑要标为尚未验证，不能包装成已复现缺陷。普通修复交还 Worker；收到新候选后确认版本，重跑失败用例与受影响的正常路径，不能用旧版本测试结果批准新代码。

## 5. 收尾判断

逐项记录已验证、失败和无法验证的要求。证据充足时按角色发布及提交协议结束；存在未覆盖的 MUST 时不要声称全部满足。返修无新增证据、环境不可用或预算不足时，把具体缺口与 CONTINUE / RESTART / STOP 的理由交回现有协议，不自建无限修复循环。

## 完整短例：独立检查发现边界缺陷

以下是虚构教学记录，候选身份、编号、路径和接口均须来自当前契约与真实记录。示例选择“返修预算已用完”的情形，不展示虚构发布回执。

**收到契约。** 冻结需求threshold_boundary：金额大于等于阈值时接受。当前候选身份由运行上下文提供。Worker称普通样本通过，E1为自测记录。

**定位并独立检查。** 使用当前read_file工具读实际候选，确认确有accepts(amount, threshold)签名，再通过当前执行工具运行以下最小检查；调用参数遵循工具schema，先按实际模块路径导入accepts。
```python
# 契约明确包含等值，预期不能照抄实现逻辑。
assert accepts(amount=9, threshold=10) is False
assert accepts(amount=10, threshold=10) is True
```
**实际返回。** 本例E2显示第一个断言通过，第二个失败，等值输入实际返回False。重新核对契约与导入候选版本后，确认测试符合要求，属于产品边界缺陷。当前返修预算已用完，因此不再调用Worker；提交失败报告请Scheduler决定是否继续。
**提交结论。** threshold_boundary尚未通过，不能列入已验证需求；引用E2，记录等值输入预期True、实际False及失败检查。整体FAILED，未批准或发布候选，建议CONTINUE供Scheduler决定。使用当前真实候选身份，按submit_code_review的schema提交报告。
若Scheduler批准继续，后续必须验证新候选版本，旧E2不能当成新版本已修好的证据。有返修预算时按既有request_code_worker_repair协议提交最小复现，再验修复结果，不套用本例的预算状态。
