# 页面候选独立验收

## 从用户行为设计检查

只依赖 code_task、当前候选和可见交接证据，不需要 Worker 隐藏思考。每项 MUST 转为“初始状态 → 输入/点击/键盘操作 → 可见结果”。先写预期再读实现；不要把候选做成什么样反向当作验收标准。区分视觉偏好与明确要求，不能临时增加设计需求。

## 分层建立证据

检查入口和引用文件是否随候选交付，构建/解析是否成功，再从真实公开入口测试可独立执行的逻辑。覆盖核心正常操作与一个会改变结论的空值或失败状态。禁止仅用源码出现按钮文字、事件名称或 CSS 规则就认定交互/窄屏可用。

实际有浏览器时再操作 DOM，检查事件、键盘焦点、反馈、布局及控制台错误；截图只支持被观察的画面。本项目沙箱默认断网，未保证浏览器或 DOM 库。缺能力时保留静态与逻辑结果，把相关 MUST 标记为无法验证，不调用不存在的工具，也不让 Worker 为获得“通过”删除视觉要求。

## 失败先归因

若模块导入或页面启动失败，核对契约入口、资源路径、依赖与测试环境；Reviewer 自己选错执行方式，应修正测试而不是返修产品。真实浏览器错误应保留最小操作序列、目标状态与实际表现。外部 API 不可达不能直接推断页面业务逻辑错误；检查受控失败反馈，说明在线链路未验证。

## 返回可执行结论

使用现有审核协议逐项给证据和缺口。例如逻辑检查通过但缺浏览器：报告“筛选结果已验证；键盘操作和窄屏未验证；需具有浏览器的验收环境”，不只说“环境不足”，也不让Worker重写已通过逻辑。本例为能力分流，不冒充已跑页面。确认产品缺陷才给操作序列、预期/实际和返修；新版本重测失败操作，旧截图不能批准新候选。
