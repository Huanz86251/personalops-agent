# 页面与交互实现

## 从契约确定状态

先读 code_task 的界面入口、MUST、目标文件与运行方式，再检查现有框架、资源路径及脚本。区分静态页面、纯前端交互和依赖后端的页面；没有后端契约时不伪造“已保存到服务器”。为主要操作列出初始、成功、空结果及相关失败状态，选择会改变用户结果的分支实现。

## 建立最小完整交互

先让一个真实入口连通：输入 → 校验 → 状态更新 → 可见反馈；再补布局与次要状态。使用语义化元素，输入有标签，按钮可键盘操作，错误能定位到字段。用户或文件内容用安全文本方式呈现，不把未知文本直接作为 HTML 执行。按已有约定处理相对路径、资源加载和窄屏布局，不因写了 CSS 就声称响应式验证完成。

## 按实际能力验证

- 静态层：检查交付文件、引用资源、入口和构建配置；解析或编译能发现语法问题，不能证明交互正确。
- 逻辑层：把筛选、计算、校验等纯逻辑通过项目测试入口或实际 Node 环境测试；覆盖一条正常输入和最易错的边界。不用字符串搜索代替执行断言。
- 浏览器层：仅在确有浏览器测试工具时检查点击、键盘、错误提示、窄屏及控制台错误。截图只能证明特定画面，不能代替交互测试。

本项目 Code 沙箱默认断网，有 Node/Python，但没有保证安装浏览器或 DOM 测试库。先检查已有依赖；不可凭空使用宿主浏览器、在线 CDN 或下载依赖完成验证。缺少浏览器时交付可运行文件及已有检查，把未验证的渲染/交互 MUST 明确留给 Reviewer，不报“视觉验收通过”。

## 交接

说明入口、启动条件、实际状态检查和未覆盖项。搜索列表可用“匹配→无结果→清空恢复”检查逻辑；DOM点击仍需浏览器。容器预检已发现没有Playwright/Chromium，因此不能写“Node检查通过，所以页面验收通过”。能测逻辑就保留结果，缺浏览器的MUST交回调度；这是能力分流，不是已实测UI成功案例。
