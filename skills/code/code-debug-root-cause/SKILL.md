# 以因果证据驱动调试

## 复现和定位

读取实际错误、输入、运行目录、环境与最近相关改动。先执行能触发问题的最小入口，记录预期与实际差异。无法复现时比较失败和成功样例的关键条件，增加针对性观测；不要把猜测写成已确认原因。

沿调用链跟踪第一个错误值或错误状态：它从哪里产生，经过哪次转换，在哪个边界偏离契约。跨模块故障分别检查输入、输出和配置是否正确传递。观测只保留判断所需数据，避开凭证与无关私有内容。

## 用检查区分原因

提出一个可验证假设，同时说明现有证据和能够推翻它的检查。比较附近工作的实现或不同输入下的行为。选择一次成本低、能区分竞争假设的实验，不同时修改多个疑似原因。

检查与假设不符时保留结果并更新解释；不要在无效修复上继续堆补丁。测试、环境和产品代码分别定位：导入路径错先修调用方法，真实业务断言失败再定位实现。

## 修复与防回归

原因明确后，在产生错误的责任边界做最小修复，并保留契约要求的其他行为。优先将最小复现变为回归检查，确认修复前后的行为差异；不能重跑旧版本时如实记录证据限制，不删除现有实现来制造失败。

先重跑原失败，再运行受影响的正常分支或调用方。返回明确失败、吞掉异常、延长等待或增加重试都需要契约支持，不能仅为让测试变绿。

## 停止条件与交接

每次重试应带来新证据。重复相同失败且无新观测时收束当前假设；若下一步需要当前沙箱没有的依赖、外部权限或超出契约的架构变化，报告已排除因素和具体所需条件。遵守现有执行与返修预算。

## 小例子

实测CSV候选：正常金额12.50通过，等于阈值0和10却漏行；最小差异指向比较符，把故意注入的 `>` 修回契约的 `>=`，同一组检查由10通过2失败变为12通过。先用边界区分“读取失败”和“过滤错误”，再改责任点；不同时重写解析、环境和筛选。
