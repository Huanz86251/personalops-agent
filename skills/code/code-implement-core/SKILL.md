# 按契约增量实现

目标是交付满足当前 code_task 的可运行候选；先打通一个可观察的行为，再扩展相关分支。以下过程按改动规模取用，不要求为简单修改另写长计划。

## 1. 确定改动边界

- 读取 code_task 的 requirements、接口约束和交付要求，把每项 MUST 对应到一个外部可观察结果。SHOULD 用于方案取舍，不能为了偏好牺牲 MUST。
- 从入口、一个真实调用者、相关实现和最近的相关测试建立调用链。先查当前目录、项目约定、解释器及测试入口；不要按其他项目的目录或包版本猜命令。
- 对照已有改动与分配的候选版本，明确哪些文件属于本次实现。接口、持久化格式或错误语义变化时，检查受影响的读写双方；纯局部修改不扩展到全仓重构。

## 2. 先确定怎样证明完成

- 对新增逻辑或缺陷修复，优先增加一个从公开入口调用、断言返回值或最终状态的回归用例。能够在修改前运行时，先确认它因目标行为缺失而失败；导入错误、缺依赖不算有效的失败证明。
- 已有测试覆盖要求时直接复用。文案、静态配置等低风险修改可用解析或针对性运行验证，无须为流程形式新增测试。
- 只替换网络、时钟等外部边界；不要把待实现的核心逻辑 mock 成预期答案。每个新增测试应能说清“哪一种真实错误会让它失败”。

## 3. 完成最小纵向路径

先连通输入校验、核心处理和可观察输出，运行最小检查，再补本任务相关的空值、失败或重复调用分支。优先复用项目现有接口和依赖；新增抽象必须解决当前重复或耦合问题。

改变输出结构时同时检查调用者；改变存储时检查写入后重读；改变异常处理时检查调用者能否区分失败与空结果。每轮失败先定位原因，再调整一个可解释的点，不靠连续添加兼容分支掩盖未知错误。

## 4. 收敛与交付

先跑目标测试，再根据调用链影响补相关模块检查。保存命令、关键结果与未验证项；已通过且输入未变化的检查无需反复跑。环境无法执行时说明缺少的依赖或能力，不声称通过。

最后检查拟交付差异：遗漏文件、临时调试输出、误带数据、接口不一致。将实现对应的 requirement ID、实际自检证据、拟交付路径和残留问题放入当前提交工具支持的字段。后续返修只解决具体缺口并重跑受影响检查。

## 小例子

CSV实测中，输出存在且正常样本通过仍漏掉等值边界；补“金额等于阈值也保留”的公开入口断言，才定位并修复比较符。增量验证应先选能区分错误实现的小样本，不把“写出文件”当作“筛选正确”。
