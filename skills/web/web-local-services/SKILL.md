# 门店与本地活动

## 定位需求

提取城市/商圈、店名/分店、日期、预算和用户关注字段。“附近”需要已给定或授权的位置，不猜用户城市。普通门店地址可直接核对；只在需要起终点路线/距离/耗时时才组合 web-map-routes。

本 Skill 被选中时，Harness 必须同时挂载 `AMAP_POI` 与 `WEB_RESEARCH`；不要因为语义路由漏召回就退回纯网页猜地点。

## 固定前门：高德找实体，网页补口碑

餐厅、门店等本地 POI 先走高德，不先用宽泛网页搜索碰运气：

1. 城市明确但没有坐标时，调用 `maps_text_search(keywords="<城市> <类别>", city="<城市>", citylimit=true)`。例如用户问“莱西有什么推荐餐厅”，先查 `keywords="莱西 餐厅"`、`city="莱西市"`。
2. 已有可靠中心坐标且用户问“附近”时，才用 `maps_around_search`；想优先发现本地热门候选可用 `strategy=1`。不要为普通全城推荐先绕道地理编码。
3. 从真实返回中保留 POI ID、名称、地址、类别等；只在候选详情确有缺口时对少量 ID 调 `maps_search_detail`，不要逐店无差别补查。
4. 先判断用户真正要求的证据强度。普通“有什么推荐/比较好的”属于软偏好：高德已返回足够实体、位置和类别时，可以明确写成“地图候选”并直接提交，不得为了把每家都包装成强口碑结论而继续扩搜。只有用户明确要求排名、评分、近期口碑、最热门、营业变化或价格，或者当前成功标准把这些列为 MUST，才再用一次 `web_search` 并行提交主查询与最多两个互补查询。例如主查询“莱西 餐厅 推荐”，补充“莱西 本地特色餐厅”“莱西 高评分餐厅”。地图结果证明实体和位置，不单独证明“最好吃”；网页口碑也不能覆盖不同分店。

网页补证必须在第一次调用时就规划好互补角度。例如餐厅任务可一次调用 `web_search(query="莱西 餐厅 推荐", alternative_queries=["莱西 本地特色餐厅", "莱西 高评分餐厅"])`，而不是三轮串行改写同一句话。三个分支用于发现不同证据，不要求每个分支都命中；地图实体加任一可信网页已经覆盖用户要求时，立即整理少量候选并提交。只有明确缺少营业时间、价格或近期评分等 MUST 字段时，才针对该字段追加一次精确查询，不为“还能更丰富”继续搜索。

2026-09-20 的当前验证：个人高德 Web 服务 Key 已成功执行 `maps_text_search(keywords="莱西 健身房", city="莱西市", citylimit=true)` 并返回真实 POI。早先 `USER_DAILY_QUERY_OVER_LIMIT` 来自公共试用源，只保留为历史故障，不代表个人源当前状态。若某次调用再次明确返回限额，不重复同一接口；记录本次地图数据不可用，再按实际证据缺口决定是否进行一次批量 Web 检索。

网页阶段用“城市 店名 分店 目标字段”核对实体，按证据缺口调整查询。结果偏题先核对同名店或减少非核心词，不机械翻页。查询里的“官方”二字不能证明搜索结果是官方发布。

## 证据分工

营业规则、服务项目和活动日期优先运营者正文；体验和设施可参考有时间、分店身份的用户记录，评分/旧排队经历不代表现在的服务承诺。价格注明人均、套餐或单品，不能混为消费总额。

分店混淆时把商圈/街道加入查询，找品牌门店目录中的具名条目，不继续堆探店文章。实测：陶陶居总店查询曾混入别店、知乎正文403；改搜“陶陶居 总店 第十甫路 官网 营业”，官网门店页读到“广州第十甫路总店”、第十甫路20号一楼及电话。地址身份缺口已补齐，营业时间未展示就继续只找总店当日安排，不套用其他分店时间。

活动平台/本地宝用于发现具名活动，再核对实际活动日和主办者；文章年份正确也可能是已结束的单日安排。正文后的公众号推广不是必须关注才能阅读。

## 失败与报告

空壳、乱码、明确拒绝和连接错误分别报告，换对应公开来源，不绕访问限制。无法核实营业、排队或余位就保留缺口，不靠摘要补答案。

输出少量符合用户条件的候选，附分店、日期、价格口径、来源与未知项。查询不授权预约、购买、登录、联系商家或发送消息；证据已覆盖请求即停止。

普通本地服务推荐只使用地图、Web Search 和公开静态来源，不因评论不足、登录墙或搜索效果不理想申请浏览器。只有用户原始请求明确要求页面操作且首次路由已挂载浏览器时，才可沿用户给出的 URL、`web_search`/业务工具返回的 URL 或当前页面实际链接操作。不凭空拼大众点评、美团等深层 URL。
