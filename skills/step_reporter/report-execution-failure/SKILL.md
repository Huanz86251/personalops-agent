# 失败原因与恢复价值审核

## 建立最小事件链

读取契约和可见 attempts，保留 attempt/assignment 身份，区分并行方向与同一任务重试。按“做了什么 → 真实返回 → 哪项标准受影响”整理；finish_reason、Worker 说明和真正工具错误不能互相替代。HARNESS_FALLBACK 或自然退出不是正式验收成功。

## 归因必须有证据

- 参数/入口错误：引用真实调用与报错，说明需要修正什么；不把猜测参数写成确定解决方案。
- 权限/环境/站点：明确登录、403、缺依赖、本地工具占用等实际观察；只有空页或超时则保留原因未知。
- 资料/内容缺口：执行成功却没找到所需实体、日期或字段，不等于工具坏了。
- 验证缺陷：结论缺证据、产物不可用、检查未运行；不以 Worker 自述填补。
- 预算/退出：说明尚未覆盖哪些标准，不把预算到限当作任务已经完成。

Reporter 无执行工具且看不到全部原始轨迹，只能审核材料中实际提供的结果；缺少原因证据时明确需要哪条错误/调用记录，不补造日志。

## 判断是否值得再试

比较同一方向最近尝试的输入、访问方式与新增证据。建议至少指出一个变化变量及可观察的成功信号：改目标字段查询、切到已找到的公开正文、修导入入口或补目标区间。只有“换网站再试”不足以安排下一次执行。相同页面持续拒绝无新能力就停止该路径；不建议代理池、绕验证码或未经授权登录。

## 分开保留成果与缺口

已证实结果放 confirmed_results，失败观测放 errors，未满足标准放 unresolved_items。需要重规划时先在 replan_reason 写明失效前提和依据，再填写 request_replan；最小恢复建议最后放 next_action。局部错误不抹掉其他有效成果，工具成功也不掩盖任务失败。只建议现有协议允许的继续/重规划/停止，不自行执行、扩充预算或改写验收要求。

实测归纳：淘宝页验证码后ZOL读到M650-M参考价269元，报告应保留参考价、注明来源和口径，缺口仅是指定店现价；若用户只要参考行情，不因淘宝失败判整步失败。Code中“零收集→修导入→收集12项”同理是验证入口修复，不是产品修复；Code走其独立Reviewer，不额外调用本Reporter。
