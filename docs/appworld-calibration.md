### 首次可定位的偏离

第 2 次工具调用开始猜测不存在的文档 API。后面还有位置参数错误、遗漏必要参数以及被拒绝的模块导入。

错误分类：不存在的 API 名称 2 次、位置参数 2 次、受限制模块 1 次、API 参数校验 1 次。

**诊断与边界：** 适配器告诉模型使用文档，却没有提供文档入口的完整参数格式。这首先是接入说明不足，应在所有正式比较组中补齐。修复这种缺口不能归因于 SkillOpt，也不应把残缺版本作为宣称提升的正式 baseline。已通过真实容器的通用 API 文档验证入口签名，修复不含任务答案。

### 第二个独立问题：截断也可能收费

两次 Step Reporter 错误均为 `LengthFinishReasonError`；服务商返回的异常结构包含输出 2,048 Token，全部为 reasoning Token。上层因此没有收到可解析的报告。

原计数器只在正常完成回调中汇总 Token，遇到这种错误会保留 unknown，未把它当零。但这些异常实际携带服务商结构化用量，可以记录。

已修复：读取异常中结构化 completion.usage；保存 usage 来源、finish reason、推理 Token、缓存输入 Token。网络超时等没有 usage 的错误仍保留 unknown。保留原始校准记录，不将修复后计数器的能力追溯套用到旧结果。

**待验证假设：** 当前输出上限不适合这一报告提示与 thinking 模式。增大上限可以减少截断，但可能增加时间与成本。第二次运行同时补齐文档并校准预算，因而只能证明接入可用性，不能用于单因素收益声明。

### 第三个记数口径

规划图报告 15 个模型轮次，独立回调实际允许开始 12 次。触达硬上限之后，规划层仍尝试发起调用，但回调在请求前拒绝。规划计数不能直接代替 API 请求计数或账单。后续可以单独修复预算耗尽时的停止路径；目前硬调用上限已生效。

## 自动诊断

`evals/appworld/diagnose.py` 仅处理 Train/Dev，拒绝最终 Test split 的逐题诊断。读取本地结果、工具轨迹与可选 Phoenix 数据库，输出错误类别、截断、用量缺失、自报与官方判分冲突、调用上限与 trace 关联。输出不包含任务正文、模型回答或工具结果原文。

检查结果用于排查，不能覆盖官方判分；错误信封也可能被模型主动打印，标签不是已证明的根因。匹配到 Phoenix 根 trace 只证明关联成功，不证明所有事件都完整导出了。

命令示例：

```text
C:/Python313/python.exe -m evals.appworld.prepare_phoenix
C:/Python313/python.exe -m evals.appworld.diagnose .agent/evaluations/<trial_id> --phoenix-db .agent/phoenix/phoenix.db
```

## 校准 2：官方通过，收尾与观测仍有边界

私有记录：`.agent/evaluations/aw_5e366f7f269f4a06a2282c057d23cf37/`。与校准 1 是同一道 Train 题；不是新增独立样本。

| 指标 | 实测结果 |
| --- | --- |
| 改动 | 通用文档入口完整签名；上限改为 24 次调用、每次 8,192 输出 Token；用量记录修复 |
| 官方结果 | 通过，2 项官方检查 |
| 模型调用 | 24 次，均正常返回到模型回调 |
| 工具执行 | 15 次，其中 1 次 API 参数校验失败 |
| 输入 / 输出 Token | 135,661 / 27,005，包含推理 Token，用量完整 |
| 墙钟时间 | 251.859 秒，不含之后的 trace flush/关闭时间 |
| Agent 最终自报 | FAILED，与官方成功不同 |
| Phoenix | 24 个模型回调均可按服务商 response ID 对应到 LLM spans；最终根 span 未落库 |

**不构成单因素提升。** 文档、调用上限和输出上限同时变化；只覆盖一题。不能写“成功率从 0% 提升到 100%”，也不能归因于 SkillOpt。正式 baseline 应从接入说明完善的版本出发，固定预算后再比较。

**自报失败为何与官方成功共存？** 工具执行已经满足任务，但 Reporter 存在 schema 校验失败，后续报告与最终 review 的请求又在全局调用上限处被拒绝。独立 grader 检查实际世界状态，判定通过。模型回调返回正常也不保证更上层 Pydantic schema 解析成功；这层故障同样需要记录。

**观测也要验收。** 第二次运行的模型调用可完整对账，但根 span 缺失。SDK force_flush/HTTP 200 不等于服务端已经完成异步入库。已在关闭自己启动的 Phoenix 之前加入只读持久化确认，失败时单独记录 trace_delivery，不改动官方成绩。零模型实际探针通过：SDK flush 返回 true，约 0.266 秒后确认根 span 已落库。旧运行缺失的根 span 不伪造补写；下一条完整 trial 仍需要检查新关闭流程。

**阶段成本仍待加强。** 尝试用真实 parent span 归属阶段时，只能明确归类 1 次 supervisor；其它 23 次的父链不足以可靠区分 executor/summary/reporter。保留未分类项，不按时间猜测后宣称精确阶段用量。后续应修复阶段关联，再决定摘要或报告哪个最值得优化。
